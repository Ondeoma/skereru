# skereru の設計

## 全体

```
           ┌──────────── HAProxy（VIP・keepalived）────────────┐
 Web/API   │ 443 → 8080（HTTP）                                   │
 MX/MUA    │ 25/587/465/143/993/110/995 → 2525…（TCP + PROXY v2） │
           └───────┬───────────────┬───────────────┬─────────────┘
                 skereru1        skereru2        skereru3      （ステートレス。どのノードでも同じ処理）
                   └───────────────┼───────────────┘
                        PostgreSQL（Patroni 3台）＋ 任意で S3 互換ストレージ
```

- アプリのノードは状態を持たない。セッション・送信待ち・総当たり対策の回数・グレイリストはすべて DB にある。
- 送信待ちは `FOR UPDATE SKIP LOCKED` で全ノードが分担する。古いデータの掃除などの定期処理は `job_lock` のリースで1ノードだけが行う。
- 変更の通知（画面の SSE・IMAP の IDLE）は、同じノードの配送はすぐに、ほかのノードの変更はメールボックスの `highest_modseq` を数秒ごとに確認して知らせる。
- 時刻で動く処理（予約送信・スヌーズの戻し・IMAP の取り込み）は、行を `FOR UPDATE SKIP LOCKED` で引き受けるので、どのノードで動いてもよい。

## メールボックスとメッセージ

- `mailbox` は IMAP のメールボックスそのもの（`uidvalidity`・`uidnext`・`highest_modseq`）。特別な用途（受信トレイ・送信済み・下書き・迷惑メール・ゴミ箱・アーカイブ）は `special_use`。
- `message` は「メールボックスの中の1通」。UID と MODSEQ はメールボックスの行を `update … returning` して払い出すので、複数ノードが同時に書いても重ならない。
  コピーは行を増やし、本体（`blob`）は共有する。
- 本体は内容の HMAC を ID にして重複をまとめ、AES-256-GCM で暗号化して保存する。どこからも使われなくなった本体は1日後に消す
  （使うときに `created_at` を更新するので、消す直前に使われたものは残る）。
- 使用量は `message` のトリガーで `app_user.used_bytes` に足し引きする。
- スレッドは `References`・`In-Reply-To` の Message-ID で同じスレッドにまとめる。
- 検索は PGroonga（`&@`）。件名・差出人・宛先は ILIKE も使う。添付ファイル（テキスト・PDF・Office・ODF）の本文も、受信のときに検索用の本文に入れる
  （展開の量・項目の数・時間に上限を付ける）。
- スヌーズは `message.snoozed_until` で一覧から隠し、時刻が来たら未読にして受信の日時を今にする（受信トレイの先頭に戻る）。

## プロトコルの実装

- SMTP・IMAP・POP3 は、接続ごとに仮想スレッド（JDK 21）で動かすブロッキングな実装。行・リテラルの読み書きと STARTTLS の切り替えが素直に書ける。
  DB などの IO は `Dispatcher` で呼ぶ（`Bridge`）。
- MIME は自前の解析器（`core/Mime.scala`）。IMAP の `BODY[1.2.MIME]` などはバイト位置で切り出す必要があるため、元のバイト列の位置を保つ。
  組み立て（送信）は Jakarta Mail を使う。
- IMAP のセッションは選択中のメールボックスの UID の並びとフラグを持ち、NOOP・IDLE・各コマンドの後で DB の `highest_modseq` と比べて
  EXPUNGE・EXISTS・FETCH FLAGS を知らせる（FETCH・STORE・SEARCH の途中では EXPUNGE を送らない）。
- ロードバランサーの後ろでは PROXY プロトコル（v1・v2）で本当の接続元を受け取る（`PROXY_PROTOCOL_FROM` の接続元だけ）。

## 受信の流れ（25番）

1. RCPT TO の時点で宛先を解決する（アドレス → `+tag` を除いたもの → キャッチオール）。存在しなければ 550。グレイリスト（任意）。
2. DATA を読む（大きさの上限、単独の LF・CR は拒否）。
3. 迷惑メールの判定: SPF・DKIM・DMARC・逆引き・DNSBL・ClamAV・規則・ベイズで点数を付ける。`SPAM_REJECT_SCORE` 以上は 550、`SPAM_JUNK_SCORE` 以上は迷惑メールへ。
4. `Return-Path`・`Received`・`Authentication-Results`・`X-Spam-*` を付けて保存する。外から付けられた同じ名前の判定のヘッダーは取り除く。
5. ユーザーごとに: 許可/拒否の差出人 → 振り分けの規則 → 容量の確認 → 保存 → 転送 → 自動返信。
   規則の転送のエンベロープの差出人はそのユーザーのアドレス。自動返信は、返信先（エンベロープの差出人）が SPF か揃った DKIM で認証されたときだけ。
6. 別名の転送先が外なら送信待ちに入れる（エンベロープの差出人は転送したアドレス）。外へ転送するメールには ARC の封印を付け、
   転送先で受信時の認証の結果を引き継いでもらう。
7. `dmarc-reports@<ドメイン>` は DMARC の集計レポートの受け口。受信トレイには入れず、解析して `dmarc_report` に置く
   （報告のメールが認証されたかも残す。このサーバーのドメインについての報告だけ）。

## 送信の流れ（587・465・Web・API）

0. 画面からの送信は、いったん `scheduled_send` に置き、取り消しの猶予（既定 10 秒）か指定した日時の後に送る（送信の取り消し・予約送信）。
   取り消すと作成の内容を返すので、作成画面に戻せる。送る途中でノードが止まったものは、二重に送らないよう送り直さずに失敗にする。
1. 認証したユーザーの From・MAIL FROM が自分のアドレス（`can_send`）か確かめる。1時間の宛先の数の上限。
2. `Date`・`Message-ID` を補い、`Bcc` を取り除き、From のドメインの鍵で DKIM 署名する。
3. このサーバーの宛先は直接配り、外の宛先は送信待ち（`outbound`）に入れる。存在しないローカルの宛先はすぐに差出人へ DSN を返す。
4. 送信待ちは MX（なければ A）に順に送る。STARTTLS は相手が対応していれば使う（`OUTBOUND_REQUIRE_TLS` で必須）。一時的な失敗は30秒から倍々（最大1時間）で再送し、
   `QUEUE_LIFETIME_HOURS` を過ぎたら差出人に DSN を返す。恒久的な失敗（5xx）はすぐに DSN を返す。

## 迷惑メールの点数（主なもの）

| 規則 | 点 |
|---|---|
| ウイルス（ClamAV） | 100 |
| 自ドメインのなりすまし（認証なし。From が複数あれば、そのすべてが認証されていること） | 10 |
| From ヘッダーが複数 | 6 |
| 1つだけのはずのヘッダー（Subject・Date・To など）が複数 | 5 |
| From のアドレスが正しくない | 3 |
| From に複数のアドレス | 2.5 |
| DMARC fail（p=reject / quarantine / none） | 8 / 5.5 / 1 |
| 実行形式の添付 | 8 |
| DNSBL に載っている | 4（ゾーンごと） |
| ベイズ 99% / 95% / 80% / 60% | 4.5 / 3 / 2 / 1 |
| SPF fail / softfail | 3 / 1.5 |
| 二重の拡張子・マクロつき Office | 3 |
| From の表示名に別のドメインのアドレス | 2.5 |
| DKIM pass / SPF pass / DMARC pass / ベイズ 1% 以下 | -0.5 / -0.5 / -1 / -2 |

ベイズの学習は、ユーザーが「迷惑メール」に移す・報告すると spam、迷惑メールから戻す・「迷惑メールではない」と報告すると ham。
本人の学習が 30 通ずつに満たないうちは全員の学習を使う。

## 認証と権限

- Web: OIDC（PKCE・state・nonce）。IdP の `sub` でユーザーを決め、初回は管理者が作ったユーザー（email が一致し未結び付け）に結び付く。
  ドメインの `auto_provision` が有効なら、IdP のメールアドレスのメールボックスを自動で作る。
- メールソフト: アプリパスワード（16文字・約75ビット。SHA-256 のハッシュを保存）。ユーザー名はそのユーザーのどれかのアドレス。
- API・MCP: APIキー（`skr_`・240ビット）とスコープ。MCP のツールは REST API を同じキーで内部から呼ぶので、権限・スコープ・監査は REST と同じ。
- CSRF: Cookie での更新系の要求は `X-Skereru` ヘッダーを必須にする（ほかのサイトからは付けられない）。
- 管理者のセッションは 8 時間（`ADMIN_SESSION_HOURS`）。グループはログインのたびに IdP から同期するので、IdP で管理者のグループから外せば遅くともこの時間で権限がなくなる。
  APIキーでのグループによる管理者の権限は、最後のログインから 7 日まで。
- MCP からは、振り分けの規則・個人の設定・管理の API を変えられない（読むだけ）。メールの本文に書かれた指示で、転送の規則などを作らせないため。
- X-Forwarded-For は `TRUSTED_PROXIES` の接続元（ロードバランサー）からのときだけ信じ、最後の値（ロードバランサーが足した値）を使う。

## 取り込み・書き出し

- IMAP: 接続情報を暗号化して `import_job` に置き、どれかのノードが引き受けて裏で取り込む（終わったら接続情報は消す）。
  接続先は確かめた IP に固定し（DNS リバインディングの対策）、内部のアドレスにはつながない。
  Gmail の「すべてのメール」は最後に読み、ほかのフォルダにないもの（アーカイブ）だけを取り込む。
- ファイル: 画面が mbox を少しずつ読んで1通ずつに分け、数 MB ずつ送る（1回の要求が短いので、ロードバランサーのタイムアウトにかからない）。
  Google Takeout の `X-Gmail-Labels` は置き場所（フォルダ・スター・未読）に使ってから外す。
- 重複は本体の ID（内容の HMAC）で見分けるので、途中で止まっても、やり直せば続きから入る。
- 書き出しは mboxrd。フォルダ・スター・未読は `X-Gmail-Labels` に書くので、取り込みで戻せる。

## 兄弟のサービスとの連携

- 会議の招待（`text/calendar`・`.ics`）は、スレッドの画面でカードにし、参加・仮承諾・辞退を iMIP の REPLY で主催者に返す。
- skuaka（カレンダー）の URL は管理者が `SKUAKA_URL` で決める（利用者が URL を決められると、サーバーから任意の場所へつながせてしまう）。
  利用者は skuaka の API トークンを設定に入れ（暗号化して保存）、招待を skuaka の予定として追加できる。
